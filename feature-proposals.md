# Предложения по развитию «Мои финансы»

Документ — аналитика, а не задание на реализацию. Решение по каждому пункту принимает человек.
Разбор сделан по `app/index.html` (766 строк) в состоянии на входе в ДЗ №2.
Код не изменялся.

---

## 1. Как приложение устроено сейчас

### 1.1. Модель данных

Единственное состояние — модульная переменная `transactions` (строка 278), массив объектов:

| Поле | Тип | Кто проверяет | Ограничение |
|---|---|---|---|
| `date` | строка `YYYY-MM-DD` | `checkDate` (358) | реальная дата, не в будущем |
| `type` | `'income'` \| `'expense'` | `checkType` (372) | только два значения |
| `category` | строка | `checkCategory` (348) | непустая, ≤ 32 символа (`MAX_CATEGORY`, 269) |
| `amount` | число | `checkAmount` (329) | > 0 после округления до копеек, ≤ 99 999 999 |
| `comment` | строка | **не проверяется** | длина и содержимое любые |

Три вещи, которых в коде не видно, но которые определяют цену любой будущей фичи:

1. **У записи нет идентификатора.** Удаление (624–633) работает через `transactions.indexOf(t)` —
   то есть по идентичности объекта, захваченного замыканием обработчика. Это работает и переживёт
   фильтрацию (замыкание держит ссылку на сам объект, а не на индекс в отфильтрованном срезе),
   но ломается на любой операции, которая пересоздаёт объекты: редактирование через
   «удалить-и-вставить», перезагрузка из CSV, undo. Идентификатор — первое, что придётся завести,
   если появится редактирование.

2. **Формат хранения совпадает с форматом обмена.** `save()` (441) кладёт в `localStorage`
   под ключом `finance.csv` результат `toCSV(transactions)`, а `load()` (445) поднимает его
   тем же `parseTransactions`, что и импорт файла. Это красиво (один путь проверки — прямое
   лекарство от BUG-013…015), но означает: **любое расширение модели данных автоматически
   становится изменением формата экспорта**. Отдельного «внутреннего» формата, который можно
   тихо поменять, в проекте нет.

3. **Схема жёстко пятиколоночная только снизу.** `parseTransactions` (406) требует
   `header[0] === 'date'` и `header.length >= 5`, а лишние столбцы просто игнорирует.
   То есть файл с шестым столбцом старым парсером прочитается без ошибки — но шестой столбец
   потеряется при следующем сохранении. Совместимость односторонняя, и это ловушка.

### 1.2. Валидация

`checkAmount` / `checkCategory` / `checkDate` / `checkType` возвращают единообразное
`{ok, value}` либо `{ok:false, error}`. Их вызывают ровно два места: обработчик формы (664–695)
и построчный разбор импорта (411–435). Это самая здоровая часть кода — новые правила
достаточно добавить в одну функцию, и они подействуют на обоих путях.

Сумма проверяется белым списком `AMOUNT_RE` (275) — регуляркой, а не `parseFloat`; это
сознательное решение (комментарий 272–274). Категория нормализуется через `categoryKey`
(382, `trim().toLowerCase()`) и `canonicalCategory` (386): написание берётся у первой
встреченной записи. `canonicalCategory` при импорте вызывается внутри цикла и линейно
сканирует уже разобранный список — квадратично по числу строк; на сотнях записей незаметно,
на десятках тысяч файл будет грузиться заметно долго.

### 1.3. Отрисовка

`renderAll()` (655) — единая точка: `renderTotals` → `renderChart` → `renderTable` →
`renderCategories`. Все четыре читают глобальный `transactions` напрямую и полностью
перерисовывают свой участок DOM через `innerHTML = ''` и пересборку узлов.

- `renderTotals` (473) — суммирует **весь** массив.
- `groupByCategory` (486) + `renderChart` (499) — группировка по `categoryKey`, сортировка
  по убыванию суммы, донат из `<circle>` со `stroke-dasharray`/`stroke-dashoffset`, палитра
  `COLORS` (263) из восьми цветов по кругу, подпись в отверстии с подгонкой кегля
  (`fitLabelInsideHole`, 570).
- `renderTable` (584) — копия массива, сортировка по дате, построчная сборка `<tr>`,
  на каждую строку вешается свой обработчик удаления с `confirm`.
- `renderCategories` (641) — заполняет `<datalist id="catList">` уникальными категориями
  **из существующих транзакций**.

### 1.4. CSV

`toCSV` (289) + `csvEscape` (283) — экранирование по кавычкам, сумма через `toFixed(2)`.
Выгрузка (707) добавляет BOM и отдаёт `Blob` через временную ссылку.
`parseCSV` (298) — честный посимвольный разбор с кавычками и переводами строк внутри полей.
Загрузка (723) построена на правиле «сначала разобрать всё, потом применить»: битый файл
не применяется вообще и не трогает текущий список, замена подтверждается через `confirm`.

### 1.5. Слабые места, которые видно сразу

| Место | Что не так | Цена |
|---|---|---|
| `renderTable`, 595 | компаратор `a.date < b.date ? 1 : -1` никогда не возвращает 0 — для записей с одинаковой датой порядок не определён и может меняться при каждой перерисовке | визуальный «прыжок» строк; ломает любые тесты на порядок |
| `save`, 442 | `catch (e) {}` — переполнение квоты `localStorage` проглатывается молча | пользователь уверен, что данные сохранены, а они нет |
| `renderChart`, 522 | палитра из 8 цветов по кругу, легенда без ограничения длины | на 9+ категориях два сектора одного цвета; на 30 категориях легенда выше диаграммы |
| `comment` | нигде не ограничен по длине, в отличие от категории | несимметрично с `checkCategory`, потенциальный раздув хранилища |
| нет `id` | см. 1.1 | блокирует редактирование и undo |

## 2. Три направления, названные человеком

### (а) Вёрстка и дизайн

**Что предлагается.** Не «переверстать», а три точечных слоя, каждый из которых
самодостаточен:

1. **Тёмная тема.** В коде уже есть полный набор переменных в `:root` (18–28) — тема
   сводится к блоку `@media (prefers-color-scheme: dark)` с переопределением тех же имён.
   Единственное место, где цвет захардкожен мимо переменных, — `fill` подписи диаграммы
   (`'#1c1e21'`, строка 561) и фон `.del:hover` (`#fbeceb`, 132). Их придётся вынести
   в переменные, и это единственная правка в JS.
2. **Визуальная иерархия карточек.** Сейчас все четыре секции — одинаковые прямоугольники
   с одинаковым весом. Блок итогов стоит выделить (акцентный фон, крупнее цифры),
   форму — сделать компактнее.
3. **Мобильная раскладка.** В брейкпоинте 760px (139–148) колонка «Комментарий» просто
   прячется (`display:none`) — данные становятся невидимыми, а не перестроенными.
   Честнее показывать комментарий второй строкой под категорией.

**На что ложится.** Почти целиком на `<style>` (17–149). Это единственная фича, которая
может почти не трогать JS.

**Подводные камни.**
- Разметка, `id` элементов и тексты кнопок **сохранены намеренно** — комментарий 14–15
  говорит, что по ним цепляются автотесты сессии 6 ДЗ №1. Переименование `id` или смена
  структуры сломает тесты, и это будет выглядеть как регресс приложения, а не тестов.
- `table-layout: fixed` и `overflow-wrap: anywhere` (119–124) — не украшательство,
  а лекарство от BUG-009/BUG-010. Замена таблицы на карточки или flex-раскладку
  переоткрывает закрытый дефект. Любая переверстка таблицы обязана заново пройти
  проверку длинными значениями.
- Тёмная тема без проверки контраста `--income`/`--expense` на тёмном фоне — это
  новый дефект доступности, а не фича.

**Объём:** S (только тема) — M (тема + иерархия + мобильная таблица).

### (б) Фильтрация транзакций

**Что предлагается.** Панель над таблицей: тип (все/доходы/расходы), категория (`select`),
период (две даты `от`–`до`), поиск по подстроке в категории и комментарии. Плюс кнопка
«Сбросить» и счётчик «показано N из M».

**На что ложится.** Новая функция `getVisible()`, возвращающая отфильтрованный срез,
и переключение `renderTable` с `transactions` на `getVisible()`. Плюс блок разметки
в секции таблицы (228–255) и стили панели.

**Ключевой вопрос, который надо решить до кода:** влияет ли фильтр на итоги и диаграмму?

| Вариант | Плюс | Минус |
|---|---|---|
| Фильтр только на таблицу | минимальная правка: трогается один `renderTable` | пользователь выбрал «Июль» и видит расходы за всё время — выглядит как баг |
| Фильтр на всё (`renderTotals`, `groupByCategory`, `renderTable`) | согласованная картина, фильтр по месяцу превращается в «отчёт за месяц» — самая ценная фича приложения | трогаются три функции из четырёх плюс `renderAll`; конфликтует со всем остальным |

Рекомендация: **фильтр на всё**, но с явной подписью в блоке итогов («за выбранный период»),
иначе цифра «Остаток» начнёт врать — она перестанет быть балансом и станет разницей
за период.

**Подводные камни.**
- Фильтр — это состояние, которого сейчас нет вообще. Класть ли его в `localStorage`?
  Скорее нет: пользователь открывает приложение и видит пустую таблицу, не помня, что
  вчера включил фильтр. Фильтр должен сбрасываться при перезагрузке — это надо решить
  сознательно, а не по умолчанию.
- Удаление под фильтром продолжит работать (замыкание держит объект, не индекс) —
  но только пока никто не «оптимизирует» обработчик до индекса. Это надо записать
  в комментарий рядом, иначе следующая правка это сломает.
- Пустое состояние раздваивается: «Записей пока нет» и «Ничего не найдено» — разные тексты.
  Сейчас `tableEmpty` (249) один.
- CSV-выгрузка: экспортировать отфильтрованное или всё? Молчаливое решение здесь —
  потеря данных на стороне пользователя. Предлагается экспортировать **всё**, а если
  экспортировать срез — то отдельной кнопкой с явной подписью.

**Объём:** M.

### (в) Справочник категорий

**Это главный архитектурный вопрос проекта.** Всё остальное — вкусовщина; здесь
принимается решение, которое трудно откатить.

**Как сейчас.** Сущности «категория» не существует. `renderCategories` (641) каждый раз
собирает `datalist` заново из уникальных `categoryKey` существующих транзакций.
Отсюда прямые следствия: удалили последнюю запись категории — категория исчезла из подсказок;
завести категорию заранее нельзя; категория расхода и категория дохода не различаются
(в `datalist` подсказываются вперемешку, хотя диаграмма их уже разделяет табами).

**Три варианта.**

| Вариант | Суть | Плюсы | Минусы |
|---|---|---|---|
| **A. Оставить как есть, улучшить** | категории по-прежнему выводятся из транзакций, но `datalist` фильтруется по текущему значению «Тип» | правка на 15 строк, ноль изменений формата, ноль рисков миграции | не решает исходную задачу: «создать категорию» по-прежнему нельзя |
| **B. Отдельный ключ в localStorage** | `finance.categories` — JSON-массив `{name, type, color?}`, независимый от `finance.csv` | сущность появляется по-настоящему; CSV не меняется, старые файлы совместимы в обе стороны | справочник **не переносится** через CSV: выгрузил на другой машине — категории потерялись; появляется второй источник правды |
| **C. Расширить CSV** | добавить служебные строки или шестой столбец | всё в одном файле, экспорт полный | ломает «CSV, который открывается в Excel» — главное свойство формата по тексту подсказки (250–254); совместимость односторонняя (см. 1.1, пункт 3) |

**Рекомендация: B**, и вот почему. Вариант C разрушает единственное внешнее обещание
приложения — что файл читается Excel'ем как обычная таблица. Вариант A задачу не решает.
B честно разводит две сущности с разной природой: транзакции — данные пользователя,
которые он выгружает и носит с собой; категории — настройка рабочего места.
Потерю справочника при переносе надо не скрывать, а компенсировать сиротами (ниже).

**Что делать с «сиротами»** — категориями, которые есть в транзакциях, но не в справочнике.
Это возникает сразу: у существующего пользователя все категории — сироты, а после
загрузки чужого CSV сироты появятся снова. Варианты:

1. **Автоподхват при старте.** При загрузке справочника все категории из транзакций,
   которых в нём нет, добавляются автоматически. Плюс: миграция бесплатна и незаметна.
   Минус: справочник нельзя «почистить» — удалённая категория вернётся при следующем
   старте, если по ней есть хоть одна запись.
2. **Показывать, но не подхватывать.** Сироты видны в подсказках, помечены как
   «не в справочнике», предлагается кнопка «добавить». Плюс: справочник остаётся
   под контролем пользователя. Минус: нужен UI, которого сейчас нет.
3. **Игнорировать.** Плохо: диаграмма покажет категорию, которой нет в списке.

Рекомендация: **1 для первой версии** (миграция обязана быть бесплатной), с оговоркой
в интерфейсе, что удалить категорию можно только вместе с её записями. Вариант 2 —
если справочник дорастёт до цветов и порядка.

**Что ещё придётся решить, и это не мелочи:**
- **Переименование категории.** Если оно есть — надо пройтись по всем транзакциям
  и переписать поле `category`. Это первая операция в проекте, которая массово меняет
  данные, и она необратима. Либо `confirm` с числом затронутых записей, либо не делать
  переименование вовсе в первой версии.
- **Удаление категории**, по которой есть записи, — блокировать (сообщением, сколько
  записей мешает), а не каскадно удалять транзакции.
- `MAX_CATEGORY = 32` и `categoryKey` (регистронезависимость) должны действовать
  на справочник тоже, иначе появятся «Кафе» и «кафе» как две разные записи справочника
  при том, что диаграмма считает их одной.
- Поле категории в форме: остаётся ли оно свободным вводом (`input` + `datalist`) или
  становится `select`. `select` — строже и дешевле в валидации, но делает невозможным
  быстрый ввод новой категории на лету, а это сейчас основной сценарий. Предлагается
  оставить свободный ввод, а справочник считать источником подсказок и порядка,
  а не белым списком. Иначе `checkCategory` перестаёт быть чистой функцией — ей
  понадобится доступ к справочнику, и импорт CSV начнёт падать на незнакомых категориях.

**Объём:** L (полноценно), M (только справочник + подсказки, без переименования).

## 3. Направления, которых человек не называл

### (г) Редактирование записи

**Зачем.** Сейчас исправление опечатки — это удалить (с `confirm`, который пугает словами
«отменить будет нельзя») и ввести заново. Для приложения ручного учёта это ежедневная
операция, и она сделана самым неудобным из возможных способов.

**Чего стоит.** Требует того самого `id` (см. 1.1). Плюс режим формы «правка вместо
добавления», плюс шестой столбец в CSV или генерация `id` при загрузке. Тянет за собой
формат — поэтому по цене это не «маленькая фича», а такая же архитектурная, как справочник.

**Объём:** L. **Рекомендация: не брать в этом ДЗ** — но зафиксировать, что удаление
на `indexOf` по идентичности объекта существует именно потому, что `id` нет.

### (д) Отмена удаления (undo)

**Зачем.** Дешёвая альтернатива предыдущему пункту и прямое лекарство от главного
страха пользователя. Удалённая запись кладётся в переменную, на 10 секунд показывается
плашка «Запись удалена. Вернуть». Возврат — `transactions.push(saved)` без всякого `id`.

**Чего стоит.** ~25 строк, одна новая функция, правка обработчика удаления (624–633),
блок разметки. Не трогает формат, не трогает валидацию. Побочно позволяет ослабить
пугающий `confirm` — но снимать `confirm` не стоит: он закрывает BUG-003, и его снятие
надо согласовывать отдельно.

**Объём:** S. Одна из лучших фич по соотношению польза/цена.

### (е) Честная работа с переполнением localStorage

**Зачем.** `save()` (441–443) проглатывает исключение молча. Приватный режим Safari,
исчерпанная квота, отключённое хранилище — во всех случаях пользователь продолжает
работать и теряет всё при закрытии вкладки, ничего об этом не узнав. Это не «дефект
удобства», это тихая потеря данных — тот же класс, что закрытые BUG-002 и BUG-011,
о которых код сам пишет «тихое искажение введённого недопустимо».

**Чего стоит.** Заменить пустой `catch` на возврат флага и показ предупреждения
через уже существующий `showError`. Плюс проверка доступности `localStorage` при старте.
~15 строк, ни формата, ни разметки.

**Объём:** S. Идеологически это самая «правильная» правка в списке: она чинит нарушение
принципа, который проект уже объявил своим.

### (ж) Стабильная сортировка таблицы

**Зачем.** Компаратор в строке 595 не возвращает 0. Записи с одинаковой датой (обычный
случай — три покупки за день) выстраиваются в порядке, который зависит от реализации
сортировки и может меняться между перерисовками. Правится добавлением вторичного ключа
(порядок добавления) — фактически одной строкой.

**Объём:** S (тривиально). Стоит приклеить к любой другой задаче по таблице,
а не выделять в отдельную.

## 5. Параллельная работа: главное ограничение

**Приложение — один файл на 766 строк, с одним блоком `<style>` и одним блоком `<script>`.
Это не мелкое неудобство, а определяющее ограничение задания.** Четыре субагента,
работающие параллельно по этому файлу, гарантированно получают конфликты слияния —
не потому, что задачи пересекаются логически, а потому, что они физически пишут
в один буфер. Ни git, ни worktrees этого не решают: worktree даёт изолированную копию,
но слияние двух версий одного 766-строчного файла всё равно делается руками.

**Правило проекта прямо запрещает выход:** «Файлов в `app/` ровно один; появление второго —
повод остановиться и спросить» (`AGENTS.md`, «Стек и версии»). То есть разнести фичи
по модулям без отдельного решения человека нельзя.

Практические выводы:

1. **Зоны нарезаются по участкам файла, а не по фичам.** Каждому субагенту называется
   диапазон: «только `<style>` 17–149», «только `renderTable` 584–639 и разметка 228–255».
2. **`renderAll` (655) — общая точка для всех.** Кто бы что ни делал, он захочет туда
   что-то дописать. Эту функцию стоит объявить зоной главной сессии и не отдавать
   субагентам вообще.
3. **Параллелить стоит не больше двух-трёх правок кода**, а четвёртого агента отдать
   на то, что не трогает `index.html` вовсе: ревью, спецификация, workflow, тесты.
   Это к тому же прямо закрывает требование «автор не проверяет сам себя».

### Матрица совместимости

| | а Вёрстка | б Фильтр | в Категории | д Undo | е Storage | ж Сортировка |
|---|---|---|---|---|---|---|
| **а Вёрстка** | — | конфликт (разметка таблицы) | конфликт слабый (форма) | конфликт слабый (плашка) | нет | нет |
| **б Фильтр** | конфликт | — | **конфликт сильный** | нет | нет | конфликт (одна функция) |
| **в Категории** | слабый | **сильный** | — | нет | конфликт (`save`) | нет |
| **д Undo** | слабый | нет | нет | — | конфликт (`save`) | нет |
| **е Storage** | нет | нет | конфликт | конфликт | — | нет |
| **ж Сортировка** | нет | конфликт | нет | нет | нет | — |

Пояснения к сильным конфликтам:

- **Фильтр × Категории.** Оба переписывают `renderCategories`/источник списка категорий
  и оба хотят вставить свой блок управления между формой и таблицей. Делать их
  параллельно — значит гарантированно мержить вручную. Только последовательно:
  сначала справочник, потом фильтр поверх него (фильтр по категории тогда получает
  готовый источник списка и становится дешевле).
- **Storage × Undo/Категории.** Все трое правят `save()` — функцию из трёх строк.
  Тот, кто делает `е`, должен идти первым и один.

### Безопасные параллельные тройки

- **Тройка 1 (рекомендуется):** `а` Вёрстка+тема (только `<style>` и две константы цвета)
  ‖ `е` Storage (только `save`/`load` и `showError`) ‖ `д` Undo (обработчик удаления
  и новый блок плашки). Пересечения — точечные, разводятся по строкам заранее.
- **Тройка 2:** `б` Фильтр ‖ `а` Вёрстка **без таблицы** ‖ ревью/документация.
- **Никогда:** `б` и `в` одновременно.

## 6. Рекомендация: что взять

Задание требует **небольшого, но доведённого до конца** результата. Крупные фичи
(`в` в полном объёме, `г`) — прямой путь к «сделали половину, не проверили».
Предлагаемый набор из четырёх пунктов:

| Что | Почему именно это |
|---|---|
| **1. Фильтрация (б)** — тип, категория, период, с влиянием на итоги и диаграмму | Единственная фича из списка, которая меняет ценность приложения, а не его вид. Записывать расходы можно и сейчас; посмотреть «сколько я потратил на еду в июле» — нельзя. Объём M, укладывается в одну сессию, результат виден на скриншоте. |
| **2. Вёрстка: тёмная тема + иерархия итогов (а, урезанная)** | Дёшево, потому что переменные уже есть. Наглядное доказательство результата. Сознательно **без** переверстки таблицы — там стоят лекарства от BUG-009/010, и переоткрывать закрытые дефекты ради красоты нельзя. |
| **3. Честный localStorage (е)** | S по объёму, но закрывает тихую потерю данных. Проект уже объявил тихое искажение данных недопустимым — этот пункт приводит `save()` в соответствие с собственным принципом. Хорошо смотрится в отчёте: находка сделана анализом, а не по ТЗ. |
| **4. Undo удаления (д)** | S, ни с чем не конфликтует, снимает главный страх пользователя. Отличный кандидат для четвёртого субагента: изолированная зона, проверяется одним сценарием. |

**Что сознательно не берётся и почему:**

- **Справочник категорий (в)** — не потому, что не нужен, а потому, что требует
  необратимого решения по формату хранения и сам по себе съест сессию.
  Правильное действие сейчас — записать в `SPEC.md` выбранный вариант (B) и вопрос
  о сиротах, и вернуться к реализации следующей сессией. Взять его вместе с фильтром
  нельзя: они конфликтуют сильнее всех остальных пар.
- **Редактирование (г)** — тянет `id` и миграцию CSV. Это не фича, это смена модели данных.
- **Стабильная сортировка (ж)** — не отдельная задача; приклеивается к фильтру,
  раз тот всё равно переписывает `renderTable`.

**Порядок работы:** сначала `е` (одиночно, трогает `save`), затем параллельно `б` ‖ `а` ‖ `д`
с явно названными диапазонами строк, четвёртый агент — на независимую проверку.
Ожидаемый прирост — порядка 150–200 строк к текущим 766, без появления второго файла
в `app/`.
